# Критический разбор каждой микроцели рефакторинга MAXIM

Редакция v4, 01.11.2026 02:14 МСК. [Исполняемый план](../operations/plans/2026-11-01-safe-refactoring-roadmap.md).
[Исходный аудит и выполненные ранее проверки](refactoring-audit-2026-11-01.md).

План v2 силён картой safety boundaries, но ещё содержал лишние prerequisites, слишком
крупные переносы и предположения о существующем покрытии. Главный выигрыш v3 — меньшая
цена принятия одного безопасного изменения. Число файлов/строк и завершение всех пунктов
не являются целью. Здесь оценены все **70 ID: 66 рабочих кандидатов и 4 отложенные границы**.
Safety review v4 добавляет [70 индивидуальных сценариев, проверок и правил отката](#safety-matrix).
Исправлены конкретные небезопасные трактовки; условия допуска реализации отмечены отдельно
от качества самого плана. Полнота этой матрицы не доказывает корректность будущего кода.
Для будущей реализации найти выбранный ID в основной оценке и safety-строке,
прочитать общий rollback legend, prerequisites и связанные contracts;
не загружать все три документа в контекст каждой маленькой задачи.

## Оценка подхода

| Критерий                                     | Оценка v2                                       | Что изменено в v3                                                                                                  |
| -------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Сохранение authority, receipts и uncertainty | Сильная основа                                  | Gates привязаны к своему entrypoint/protocol; live effects не требуются для pure move                              |
| Размер одного результата                     | Неравномерный                                   | B04 — один caller, F02 — presentation, F05 — query/terminal, mutation family отдельным следующим срезом            |
| Правильность prerequisites                   | Частичная                                       | Убраны semantic cycle A07/V03 и unrelated file-split/parser/UI dependencies                                        |
| Доказательство пользы                        | Гипотезы без свежего workload baseline          | Existing work исключено из нового выигрыша; A10/P01 — маленькие воспроизводимые измерения                          |
| Пригодность для агентов                      | Хорошая карта, дорогая универсальная подготовка | Scope-specific cards, conditional adapters/inventories, поддерживаемые selective или честные whole-family commands |
| Готовность к реализации                      | Зависит от конкретного ID                       | План завершён, но pending case/contract/reader evidence остаётся gate, а не фиктивным pass                         |

Польза/риск в таблицах — относительная инженерная оценка минимального среза: **В** —
высокая/высокий, **С** — средняя/средний, **Н** — низкая/низкий. Это не измеренный процент
ускорения. «Условно» означает выполнять лишь при указанном основании; «отложить» не
делает ID частью текущей release очереди. У исследовательской карты риск чтения низок,
даже если реализация её protocol имеет высокий риск. Подробные acceptance/rollback gates
остаются в плане и соответствующих domain references.

## Что меняет свежий main

[Native storage на 3096266b1](https://github.com/GameclubPro/Major-Maksimov/blob/3096266b1f81ab50b82da759293fbcc5483f2ead/apps/miniapp/src/lib/native-storage.ts#L34)
считает MAX web SDK storage недоступным даже при существующих методах. Слои storage/recovery сохраняют различия
между native read error, missing, corrupt и conflicting. `saveMirroredItem(): void`
по-прежнему best effort: возврат из функции не доказывает durable commit.

[Marketplace panel](https://github.com/GameclubPro/Major-Maksimov/blob/3096266b1f81ab50b82da759293fbcc5483f2ead/apps/miniapp/src/pages/settings/karavan-marketplace-panel.tsx#L69)
разделяет daily management с подтверждённым binding/access и connection recovery. Их
нельзя снова объединить одним loading/error gate. Connection recovery запрашивается для
connection actions и удерживает запрошенный scope; current editor не размонтируется лишь
из-за ошибки этого recovery. Server authority и отдельный IDB daily-command journal остаются.

[Binding hook](https://github.com/GameclubPro/Major-Maksimov/blob/3096266b1f81ab50b82da759293fbcc5483f2ead/apps/miniapp/src/pages/settings/use-karavan-marketplace-binding.ts#L77)
сохраняет original chat/key/request и attempt token. Retry проходит journal fence с тем
же command ID; поздний ответ другого actor/operation не удаляет чужую evidence. Лишь строго
более новая same-chat generation может оградить старую uncertain operation; equal/missing
не превращают unknown в terminal success. Это конкретные future regression invariants,
не основание писать общий mutation/localStorage hook.

Новые native-storage, binding-hook и marketplace cases прочитаны. Их web/mocked API/IDB
harness не доказывает настоящий DeviceStorage, MAX WebView или live provider compatibility.
Generated TSX внутри browser script дополнительно относится к C04 typecheck gap.

## Практическое решение после оценки

Сначала A01 и узкий evidence/preflight выбранного scope. Для CI gap — A02/A12 → один A03
с A11. Для малого structural runtime результата рассмотреть T04 либо F03; для tooling
есть конкретный V04. Это варианты выбора одного этапа, не параллельная программа.
S02 остаётся отдельной correction; U03/U04 требуют собственного U02; F02 сохраняет
immediate persistence; P02 возможен лишь для ещё не оптимизированного reader после P01.

A04/A07/V01–V03/V05/V06/O02 допускают отказ от нового abstraction при недостаточной пользе.
B05 не обязан доводить allowlist до полного разрыва с Admin любой ценой. Наличие малой
границы ещё не доказывает throughput/latency выигрыш. После двух принятых runtime срезов
выбирать продолжение по фактическому контексту, цене feedback и correctness evidence.

Защитный результат review — ни одна карта/таблица не разрешает replay uncertain effects,
очистку queues/stores, новое DDL или публикации в группах. Persisted/reader изменения имеют
отдельный rollback class; application revert не подменяет settlement внешнего эффекта.

## Safety matrix

Матрица проверяет **все 70 ID** на безопасность. В каждой строке указан конкретный
сценарий регрессии, положительный контроль и отказ/запрещённый эффект, допустимый возврат
и gate. Это требования к выбранному будущему срезу; новые перечисленные тесты пока
не исполнены. Общий gate плана и scoped notes обязательны сверх строки.

Допуски: **исследование** — карта/локальный controlled measurement; **условно** — узкая
реализация после baseline и stated gates; **стоп до gate** — указанный runtime edit или
активация adapter не допускается до названного proof. Подготовить недостающий локальный
test/fix можно отдельным обратимым prerequisite. **Отложено** не является release queue.
Для CSS/async/schema строк «стоп» относится к своему missing corpus, а не всему проекту.

Классы отката:

- **N:** чтение/документы; исправить гипотезу/evidence, убрать только owned temporary data.
- **T:** tests/tooling; согласованно вернуть owned files/consumers и убрать только свои
  процессы/stores/fixtures, сохранив coverage. Runtime deploy не требуется.
- **C:** совместимый code/image rollback на допустимый target через штатные CI/release
  gates. Неизменны durable formats, versions, keys, schema и authority; это не DB restore.
- **D:** изменение persisted/schema/reader protocol требует отдельного compatibility
  решения для old/new readers/writers и in-flight operations. Неразрешённый failed/unfinished/ambiguous
  migration receipt либо partial schema блокирует обычный revert/redeploy до reviewed
  bounded schema+receipt recovery. Finished migration list этого не доказывает; текущие
  узкие примеры — [rollback preflight](../../infra/scripts/vps-runtime-rollback.sh) и
  [schema recovery check](../../infra/scripts/message-retention-recovery-schema.mjs).
  Никаких auto down/DROP/migrate resolve/checksum edits или новых live SQL из матрицы
  не следует. Чистому code move не назначается blanket production DB scan.
- **E:** поверх C/D сохранить command/lease/attempt/receipt/unknown fences. Только
  существующий settlement/reconciliation по точной evidence; rollback не разрешает
  повтор SEND/DELETE, выдачу нового command ID или fabricate completion.

C для UI/stateful целей действует только при неизменном формате хранилища. Любой
incidental persisted drift останавливает mechanical scope и переводит его в D, даже
если D не повторён в клетке. Runtime pair proof нужен лишь затронутому contract;
карта/pure move не запускают отдельный live rollout или provider mutation ради проверки.
Если два среза делят state/schema/CSS/runner, второй обновляет baseline на принятом SHA
первого. Один общий helper у implementation и expected не даёт независимого proof.

При затронутом lazy graph/assets/CSS отдельно проверить caller-specific auto/manual policy,
asset/export marker, blocked sessionStorage, missing chunk и повторный сбой без loop;
Сохранить существующую persistence/flush policy выбранного draft; обещанный durable draft
должен пережить recovery. Новая персистентность in-memory draft не входит в перенос.
Не навязывать одинаковый reload всем callers.
[recoverable-lazy](../../apps/miniapp/src/lib/recoverable-lazy.ts) явно проверяет named export,
но [lazy-pages](../../apps/miniapp/src/pages/lazy-pages.ts) не имеет того же runtime check.
Этот existing gap не считается покрытым fallback и не исправляется массово внутри pure move.
