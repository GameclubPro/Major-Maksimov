The connector derives and forwards `MAXIM_SCALE_EXPECTED_REPO_DIR`; it does not use production defaults or cloud SSH authorization/fallback for scale.

Missing identity evidence stops the command. Admission does not provision a host or certify application credentials, stores or MAX destinations: verify those test-only resources separately before an actual load test, preserving every cold-maintenance, source and capacity gate.
- Scale source synchronization pins the fetched commit and rejects a target that removes the host-admission entrypoint wiring or changes the trusted guard helper. It validates an existing local target branch before checking it out, uses only the admitted commit for fast-forward merge, and rechecks host identity, exact HEAD and complete synchronized controller bytes before re-exec. The continuation retains that commit under the inherited protected lock without fetching a new ref; a caller's re-exec flag cannot suppress a required controller restart. Install a reviewed guard-helper update through the normal guarded tooling path first; `deploy-scale` cannot upgrade or downgrade its own admission contract.
- Keep `MAXIM_VPS_AUTO_AUTHORIZE_SSH=0` and Yandex VM/security-group settings out of the REG.RU `.env.vps`. Yandex SSH helpers are legacy-only and cannot recover this host.
- If REG.RU SSH stalls before the banner, check the destination, local network, provider firewall and host UFW/sshd. Use the REG.RU server console/IPMI for recovery; retain strict host-key verification.
- GitHub Actions Deploy is manual-only. Local `vps-connect.sh deploy` is the routine path unless hosted-runner SSH reachability is known to work.
- Deploy and rollback scripts run on the backend VPS. Invoke them locally only through the wrapper/SSH.
- Incident evidence must retain exact time/release boundaries, truncation/gaps and an allowlisted failure stage/code. Run `postgres-audit` catalog calls sequentially (shared lock); never substitute inline live SQL. For shell-over-stdin diagnostics, redirect non-reading child commands from `/dev/null` and require every expected stage, since exit zero alone may describe an incomplete probe.

It does not evaluate the runtime materializer or authorize settlement/replay. Synchronize reviewed tooling and review the separate audit-role provisioning preview first. See [held removal metadata](../operations/runbooks/webhook-owner-proof-audit.md#held-removal-metadata).
- Resolve release-blocking readiness/smoke failures autonomously within the authorized task. Diagnose the exact failing stage and runtime before changing it; a proved corrective runtime can ship through the normal stopped-worker fence from a degraded baseline, with green exact-SHA CI and strict post-release checks. Never extend a timeout, suppress readiness, clear queues or repeat an unchanged rollout to manufacture success.
- `postgres-audit moderation-outcomes [--bot <bot-id>] [--explain]` samples at most 512 recent moderation events after an indexed 513-row sentinel. Schema v3 retains ban/mute/voice rows, fixed rule families, evidence levels, metadata admission and the actual sample span. Additive `stop_words_rows` separates words/domains/OCR detection, fixed guard refusals, verified deletes and unknown outcomes without source text. Global newest events can omit quieter bots; obtain IDs from the configured registry and collect exact scopes sequentially through the existing bot/time index. Scoped plain EXPLAIN uses a generic prepared parameter to avoid emitting the ID. Event-only counts, recorded times, rejected compressed/oversized metadata and truncated samples do not prove eligible input coverage, command latency, current mute state, filter accuracy or fleet recovery. Review the plain plan before the report; no new database grants are needed. See [stop-word audit](../operations/runbooks/stop-words-policy-rollout.md#bounded-audit) and the [moderator audit plan](../operations/plans/2026-10-20-moderator-production-optimization.md).
- Keep Yandex and VK Cloud credentials in ignored local files or configured CLI profiles; never print or commit service-account keys.

## Offline Capacity Comparison

The local [report](../../infra/scripts/monitor-capacity-report.cjs) reads the private
archive created by `monitor-readonly`, without SSH, database or MAX calls. Set actual
captured UTC windows; do not reuse a historical release's sample dates:

```bash
: "${CAPACITY_FROM:?Set the captured window start in UTC ISO format}"
: "${CAPACITY_TO:?Set the captured window end in UTC ISO format}"
node infra/scripts/monitor-capacity-report.cjs --from "$CAPACITY_FROM" --to "$CAPACITY_TO"
```

Optional `--compare-from` and `--compare-to` select an earlier, non-overlapping window
of equal duration. Each window must span 1–60 minutes and already have ended.
`--archive-dir` selects the private archive instead of its default XDG state location.
Missing files, sparse samples, stale/unknown data, reset counters and unfinished windows
are not successful observations. `status` covers the entire interval; `last` is only
its final snapshot. Retain the report's private-file, bounded-input and redaction rules.

Report schema 2 uses `sampled_oldest_queue_lag_and_container_generation_intervals`.
Raw `lagSec` and `operationalLagSec` percentiles
remain separate, with explicit `operationalLagCoverage`. Old records without operational
values remain unavailable; never substitute zero or raw age. A lower p95 under different
traffic is descriptive, not a causal speedup. Readiness, closed cohorts and actual action
outcomes remain separate evidence, especially for waiting or quarantined events.

API/OCR/photo restart deltas require adjacent archived observations of the same verified
container generations, with both interval endpoints inside the selected window. The first
in-window observation is only an anchor. Missing intermediate records, new sessions, resets,
replacements and legacy totals cannot provide complete restart coverage or a healthy/comparable
window. Positive confirmed deltas still report degradation when other evidence is unknown.
`historicalRestartDiagnostic` retains old total-counter arithmetic explicitly as a diagnostic;
equal totals never prove that no container restarted or was replaced. Restart causes remain
unknown without independent evidence.

Unavailable fleet observations may include `observationFailure` version 1 with an
allowlisted `stage` and `code`. Stages identify expected services, release manifest,
source Git/topology, Docker list/inspection, inspection parsing/census or fleet summary.
Command codes distinguish cancellation, timeout, output cap, spawn, nonzero exit and
signal exit; validation and census failures remain separate. These are collector
failure observations, not evidence of a restart or its cause. Raw commands, output,
errors and container identities are never archived or printed. Healthy fleet results
retain their existing shape; old or invalid diagnostics retain an unknown cause.
`fleetObservationFailures` counts finite stage/code buckets and separates failed
observations without a known cause from missing fleet metadata. Diagnostics do not
change alerts, sampling bounds, retry policy, coverage or restart interval rules.
`missingSamples` counts archived snapshots without valid fleet metadata; absent
sample timestamps remain separate coverage gaps.

[Report regressions](../../infra/scripts/monitor-capacity-report.test.mjs) cover bounded
archives, coverage, redaction, counter resets and invalid comparison windows.
