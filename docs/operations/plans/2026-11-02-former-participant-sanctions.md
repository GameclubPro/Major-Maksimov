# Санкции для ушедшего участника

Основание: пользователь 2 ноября 2026 поручил разрешить мут и бан через «События»
после выхода участника и заменить непонятное «Без сообщений» на «Мут» без лишнего
текста в интерфейсе. Это решение меняет прежний запрет санкций для отсутствующего
участника, но не расширяет права на защиту участника или действия в других чатах.

## Поведение

| Сценарий                                                           | Результат                                                                                                              |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| Участник вышел, его история подтверждена в выбранном чате          | Карточка разрешает мут и бан; защита остаётся недоступной.                                                             |
| Мут ушедшему                                                       | Сохраняется обычный мут по чату и пользователю. Срок идёт от назначения, после возвращения действует оставшееся время. |
| Бан ушедшему                                                       | Сохраняется бан этого чата с режимом `LOCAL_REJOIN`. При возвращении бот удаляет участника.                            |
| Повторное возвращение                                              | Пока бан действует, новый подтверждённый вход допускает новое удаление.                                                |
| Пропущено событие входа                                            | Новое сообщение позволяет повторно проверить и применить действующий локальный бан.                                    |
| Снять локальный бан                                                | Отменяется сохранённый запрет; MAX-вызов возврата или удаления не выполняется.                                         |
| MAX не подтвердил отсутствие или права                             | Ошибка не превращается в доказательство выхода и не разрешает санкцию.                                                 |
| Сам администратор, владелец, администратор чата или защищённый бот | Существующие запреты сохраняются, в том числе непосредственно перед удалением.                                         |

`LOCAL_REJOIN` не гарантирует запрет самого входа в MAX. Нативные режимы
`MAX_BLOCK` и `MAX_REMOVE_ONLY` для действующих участников сохраняются.
Режимы каналов и глобальный список спамеров не меняются. Выбор нескольких чатов
остаётся явным; новая санкция не выводится из старых событий BAN без точного режима.

## Реализация

1. Разделить серверные возможности мута, бана и защиты. Сверять точный чат,
   пользователя, историческое подтверждение и текущие права администратора и бота.
2. Использовать существующий журнал санкций и блокировку изменения санкции.
   Новый `MANUAL_BAN` имеет точный режим `LOCAL_REJOIN`; сохранение и аудит
   не требуют нативного запроса к отсутствующему участнику. Последняя санкция,
   её снятие и защитные записи остаются под действующим правилом retention.
3. Выполнять локальное снятие до экспериментального или нативного UNBAN.
   Проверять выбранную санкцию, сохранять событие снятия и обновлять runtime.
4. Вход и сообщение вызывают один ограниченный обработчик бана. Он проверяет
   действующую санкцию, её fence, права точного исполнителя и текущую роль цели
   под санкционной блокировкой и повторяет проверку на границе MAX-вызова.
   Удаление использует обычный `KICK_MEMBER`, сохраняет дедупликацию источника
   и неопределённый результат; старое действие не повторяется ради нового входа.
5. Не привязывать ручной бан к `deleteSpammersEnabled`. Не отправлять уведомления
   в чат. Успешно удалённый участник не получает приветствие.
6. Обновить карточку, журнал и список ограничений: «Мут», «Бан», «Снять мут»,
   «Снять бан». Сохранить срок, область и существенные последствия операции.
   Новые возможности санкций не включают заодно защиту участника.

## Проверки и выпуск

- Сначала точечные тесты: подтверждённый выход, неизвестное членство, чужой ID,
  свои и защищённые аккаунты, срок мута, точная область, локальный UNBAN без MAX.
- На PostgreSQL/Redis: сохранение и перечитывание санкции после потери кэша,
  повторный вход, снятие или замена во время ожидания, потеря lease, сохранение
  неопределённого исхода и отсутствие зависимости от списка спамеров.
- На локальном PostgreSQL с 20 000 строк истории: действующий, отсутствующий и
  снятый бан проверяются реальным `readActiveLocalChatBan`. Его точный SQL и
  параметры, включая проверку fence, берутся из Prisma query events и измеряются
  через `EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, FORMAT JSON)` без принудительного
  выбора индекса. Для каждого сканирования допускается не более восьми просмотренных
  строк, для запроса — не более 64 shared blocks. История включает свежие обычные
  события цели, санкции других пользователей того же чата, санкции того же
  пользователя в другом чате и чужие fence того же чата.
- В браузере: iPhone/Android, светлая/тёмная темы, события → нужная карточка,
  независимые возможности санкций и защиты, выбор срока/чатов, короткие подписи,
  снятие локального бана при недоступном нативном восстановлении MAX.
- Оба механизма отката должны отвергать образ без чтения `LOCAL_REJOIN`,
  локального снятия и runtime-обработчика. Bootstrap обязан распознать обновлённый
  контроллер; наличие версии без рабочих вызовов не доказывает совместимость.
- Финальная проверка принадлежит staged commit helper. Для точного SHA нужны
  `Required` и `Analyze JavaScript and TypeScript`, затем обычный `deploy main --auto`
  со всеми ролями общего API-образа и затронутыми статическими компонентами.
- После выпуска: синхронизированный SHA, immutable manifest и строгие smoke.
  Проверки на реальных людях и диагностические публикации в чатах не допускаются;
  локальная проверка, CI, выпуск и реальная приёмка MAX учитываются отдельно.

Для запроса последнего состояния фиксированный литеральный предикат должен
совпадать с `moderation_events_sanction_user_state_idx`: параметры enum с
преобразованием через `cstring` не обеспечили применимость partial index в
локальном плане. Проверка fence без отдельного индекса просмотрела 4 000 чужих
строк и 478 shared blocks через `moderation_events_chat_rule_created_id_idx`.
Поэтому миграция `20261102023205_index_sanction_fence_user_state` конкурентно
добавляет partial index по точному чату, пользователю и порядку событий с
`rule_code = 'SANCTION_STATE_FENCE'`. Он сохраняет все фазы и intended actions;
фильтрация metadata и правила недействительности санкции остаются прежними.
