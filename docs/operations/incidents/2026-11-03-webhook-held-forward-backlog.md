# Затор подготовки webhook 3 ноября 2026

## Наблюдение и причина

В 16:59 UTC ограниченный аудит показывал не менее 2000 `RECEIVED`;
лимит выборки был достигнут. Старейшее событие поступило в 16:17:00 UTC,
не имело попыток постановки в очередь и сохраняло причину
`legacy_scope_unsealed`. База и Redis отвечали. Сохранённая причина оказалась
недостаточно точной: адресный аудит обнаружил существующее запечатанное
ограничение и современную пересылку с link markup и единственным SHARE preview.
Старый строгий проектор не поддерживал эту форму. Это доказательство причины
конкретного блокирующего события, а не всех записей выборки.

Исходный работающий API имел ревизию
`14d4d007ce44dde9e9a517cfd37912e4e13796a5`. Незавершённый предыдущий выпуск
оставил валидированный переходный журнал без текущего component manifest.
Исправление опубликовано в
[PR #456](https://github.com/GameclubPro/Major-Maksimov/pull/456).

## Исправление и выпуск

Изменение расширяет только проекцию допустимых CREATED-пересылок после
существующего seal. Сохраняются проверки всех совпадающих ограничений,
исходной структуры, отсутствия попыток исполнения и чужих execution claims.
Результат — `NO_REPLAY_HELD`, без вызова исходного обработчика и MAX.
Постоянные ограничения источника и участника сохраняются. Подробнее —
[регламент восстановления](../runbooks/legacy-webhook-order-recovery.md).

Локально прошли 291 unit-проверка и 183 проверки на настоящих PostgreSQL 16
и Redis 7 без пропусков по хранилищам. Для точного merge SHA
`fa8ffbf25713e08238582c214c32b6a786170575` успешны Required и CodeQL.
Штатное продолжение выпуска с явным принятием единственного проверенного
журнала выполнено 18:49:41–19:00:38 UTC, exit 0. Полная сверка установила
этот SHA для общего API, обеих статик и Ластика; хранилища не пересоздавались.
Все обязательные API/native/static проверки прошли, component manifest
зафиксирован штатным deploy.

Прежнее старейшее событие стало `NO_REPLAY_HELD`: попыток enqueue по-прежнему
ноль, задания нет, указатель на legacy proof сохранён. Оно не объявлено
`PROCESSED`, и внешний эффект этим результатом не подтверждается.

## Приёмка и границы

После выпуска в окне 19:01:22–19:16:25 UTC получен 61 успешный sample.
HTTP readiness — 200, PostgreSQL и Redis — доступны во всех samples;
обе измеряемые задержки ниже 10 секунд, максимум — 2,88 секунды.
Максимальный интервал между samples — 22,67 секунды при допустимых 35.
Последний sample: задержка 0,76 секунды, режим `normal`, состояние `healthy`.

В ограниченном аудите 19:17:03–19:17:04 UTC `RECEIVED=0`, `QUEUED=0`,
лимиты этих двух выборок не достигнуты. Это снимок активной очереди,
которая продолжает принимать обычный трафик.

Исторические `FAILED` и карантин сохранены; их повторная обработка не
разрешалась. Приёмка подтверждает разгрузку активной очереди и доступность
в указанном окне, но не все функции восьми ботов, права каждого сообщества
или внешние результаты каждого исторического события. Сырые журналы,
точные идентификаторы и heartbeat наблюдателя сохранены в приватном task record.
